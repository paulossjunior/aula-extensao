## Introdução

Até aqui trabalhamos com **um agente por vez**: você descreve, ele executa, você revisa. Funciona bem para tarefas com um único fio condutor. Começa a travar quando o trabalho tem frentes distintas que exigem competências distintas — pesquisar o problema, escrever a spec, implementar, revisar, documentar.

O **[CrewAI](https://github.com/crewAIInc/crewAI)** propõe outra unidade de trabalho: em vez de um agente genérico, uma **equipe de agentes com papéis definidos**, cada um com objetivo próprio, ferramentas próprias e tarefas atribuídas. É a mesma ideia de divisão de trabalho que vocês aplicaram no Scrum da Aula 07 — só que os executores são agentes.

E aqui vem o ponto que vale a aula inteira: **orquestrar mais agentes é uma aposta em velocidade**. O framework PSM CID, que vimos na Aula 01, é explícito ao dizer que ênfase excessiva em velocidade cobra o preço em qualidade. Então não basta montar a *crew*: é preciso **medir se ela realmente acelerou e se a qualidade se manteve**.

## Discovery do Projeto

### O que é o CrewAI

| Item | Valor |
|------|-------|
| Descrição | Framework de orquestração de agentes de IA autônomos com papéis |
| Licença | MIT |
| Linguagem | Python (>=3.10, <3.14) |
| Site e documentação | [crewai.com](https://crewai.com) · [docs.crewai.com](https://docs.crewai.com) |

O projeto se define como um framework Python de código aberto, com abstrações de alto nível e APIs de baixo nível, para construir fluxos multiagente prontos para produção.

---

### As duas abstrações: Crews e Flows

O CrewAI oferece dois caminhos complementares, e entender a diferença evita a maior parte dos erros de projeto.

| | **Crews** | **Flows** |
|---|---|---|
| Otimiza para | Autonomia e inteligência colaborativa | Controle preciso e determinismo |
| Como funciona | Agentes com papéis decidem e delegam entre si | Fluxo orientado a eventos, com estado e ramificação |
| Use quando | O caminho da solução não é conhecido de antemão | O processo é conhecido e precisa ser confiável |
| Risco | Comportamento menos previsível | Menos flexível diante do inesperado |

- **Crews** entregam decisão autônoma entre agentes, delegação dinâmica, papéis especializados com objetivos definidos.
- **Flows** entregam controle fino do caminho de execução, estado consistente entre tarefas, integração limpa com código Python de produção e ramificação condicional.

!!! tip "A combinação é o padrão de produção"
    A documentação recomenda usar os dois juntos: o Flow dá a espinha determinística do processo, e chama Crews nos pontos onde a autonomia ajuda. Traduzindo para o nosso curso: **o pipeline é Flow, o trabalho criativo é Crew**.

---

### Anatomia de uma Crew

Quatro conceitos e nada mais:

| Conceito | O que é |
|----------|---------|
| **Agent** | Um papel, com `role`, `goal` e `backstory`. É quem executa |
| **Task** | Uma unidade de trabalho, com `description`, `expected_output` e o agente responsável |
| **Crew** | O conjunto de agentes e tarefas |
| **Process** | Como as tarefas são encadeadas — sequencial ou hierárquico |

!!! abstract "Onde isso já apareceu no curso"
    `Task` tem `description` e **`expected_output`**. Isso é exatamente o que vocês escreveram como **critério de aceitação** nos cenários Gherkin da Aula 13 — a diferença entre pedir "faça um relatório" e definir o que caracteriza o relatório pronto. Spec ruim gera código ruim, com um agente ou com cinco.

### Instalação e projeto

```bash
uv pip install crewai
uv pip install 'crewai[tools]'      # com as ferramentas extras

crewai create crew meu-projeto
```

O comando gera a estrutura:

```text
my_project/
├── pyproject.toml
├── .env
└── src/my_project/
    ├── main.py            # ponto de entrada, entradas customizadas
    ├── crew.py            # definição da crew, lógica e ferramentas
    ├── tools/
    └── config/
        ├── agents.yaml    # definição dos agentes
        └── tasks.yaml     # definição das tarefas
```

A configuração fica em YAML, separada do código:

```yaml
# config/agents.yaml
researcher:
  role: >
    {topic} Senior Data Researcher
  goal: >
    Uncover cutting-edge developments in {topic}
  backstory: >
    You're a seasoned researcher with a knack for uncovering the latest
    developments in {topic}.

reporting_analyst:
  role: >
    {topic} Reporting Analyst
  goal: >
    Create detailed reports based on {topic} data analysis
  backstory: >
    You're a meticulous analyst with a keen eye for detail.
```

```yaml
# config/tasks.yaml
research_task:
  description: >
    Conduct a thorough research about {topic}
  expected_output: >
    A list with 10 bullet points of the most relevant information about {topic}
  agent: researcher

reporting_task:
  description: >
    Review the context you got and expand each topic into a full section.
  expected_output: >
    A fully fledged report with the main topics, each with a full section.
  agent: reporting_analyst
  output_file: report.md
```

```python
# crew.py
from crewai import Agent, Crew, Process, Task
from crewai.project import CrewBase, agent, crew, task
```

!!! note "Configuração fora do código é decisão de arquitetura"
    Papéis e tarefas em YAML versionado significam que **a equipe de agentes é revisável em pull request**, como qualquer outro artefato. É o mesmo princípio da constitution do Spec-Kit na Aula 09: o comportamento do agente vira arquivo, não conversa perdida no chat.

---

### Quando usar — e quando não

A própria documentação delimita: use CrewAI quando o trabalho exige **mais do que um prompt ou um chatbot** — múltiplos passos, agentes especializados, uso de ferramentas, saídas estruturadas, revisão humana, ou fluxos que misturam raciocínio autônomo com regra de negócio explícita.

!!! warning "O erro clássico: orquestrar cedo demais"
    Montar cinco agentes para uma tarefa que um agente resolve adiciona custo, latência e pontos de falha — sem ganho. Antes de criar uma crew, responda: **quais frentes deste trabalho são realmente independentes?**

    Vocês já têm a ferramenta para responder isso: a **DSM da Aula 07**. Tarefas sem dependência entre si são candidatas a rodar em paralelo; tarefas encadeadas não ganham nada com orquestração.

### Medindo a orquestração com o PSM CID

Esta é a parte que fecha a aula. Multiagente é uma **aposta de velocidade na Factory** — a região do [Diagrama de Contexto de Medição (Figura 2 da Aula 01)](aula-01-2026-08-03.md#2-contexto-de-medicao-onde-cada-medida-nasce) que vai do backlog ao deploy. Toda aposta de velocidade precisa de contraprova de qualidade.

| Medida do PSM CID | O que ela responde sobre a sua crew |
|-------------------|--------------------------------------|
| **Cycle Time** | Do início da execução até a conclusão — a crew realmente encurtou isso, ou só distribuiu a espera? |
| **Lead Time** | Da identificação do trabalho até a entrega. Inclui o tempo gasto configurando a crew |
| **Cumulative Flow** | O trabalho está fluindo pelos estados, ou empilhando em revisão humana? |
| **Committed vs. Completed** | A crew entregou o que se comprometeu a entregar? |
| **Defect Detection** | Quantos defeitos foram **contidos** antes da release e quantos **escaparam** |
| **Automated Test Coverage** | A trava que segura a qualidade quando a geração de código acelera |

!!! danger "O ponto de equilíbrio velocidade × qualidade"
    A [Figura 8 da Aula 01](aula-01-2026-08-03.md#7-principios-de-medicao) mostra o *sweet spot*: ênfase excessiva em velocidade custa qualidade do produto; ênfase excessiva em qualidade derruba a entrega. **Multiagente empurra o cursor para o lado da velocidade.**

    Se a sua crew triplicou a produção de código e dobrou os defeitos escapados, ela **piorou** o produto. Sem medir, o time não tem como saber de que lado do ponto de equilíbrio está.

O framework também observa que algumas melhorias — **automação, principalmente** — deslocam as duas curvas ao mesmo tempo. Uma crew que gera código **e testes** é diferente de uma que só gera código.

## Tarefas

### Tarefa 1 — Primeira Crew

**Duração estimada:** 20 min
**Formato:** Duplas

1. Instale o CrewAI e rode `crewai create crew <nome>`
2. Edite `agents.yaml` com **dois agentes** ligados ao produto do grupo — por exemplo, um que analisa requisitos e um que escreve a documentação
3. Edite `tasks.yaml` com uma tarefa para cada, cuidando do `expected_output`
4. Execute e guarde a saída

**Entregável:** Projeto rodando, com os dois YAML e a saída gerada.

---

### Tarefa 2 — Recortar as Frentes com a DSM

**Duração estimada:** 15 min
**Formato:** Grupos

Peguem a **DSM do grupo**, da Aula 07, e respondam:

1. Quais tarefas do produto **não têm dependência** entre si?
2. Dessas, quais justificam um agente com papel próprio?
3. Onde o processo é conhecido e determinístico — ou seja, deveria ser **Flow** e não **Crew**?

**Entregável:** Desenho da crew do grupo, com papéis justificados pela DSM.

---

### Tarefa 3 — Medir Antes e Depois

**Duração estimada:** 25 min
**Formato:** Grupos

O exercício central da aula. Peguem a **user story que o grupo implementou na tarefa de casa da [Aula 13](aula-13-2026-11-16.md)** — ou outra tarefa real do backlog — e executem duas vezes:

| | Execução A — agente único | Execução B — crew |
|---|---|---|
| **Cycle Time** | tempo do início até concluir | tempo do início até concluir |
| **Defeitos contidos** | encontrados antes de integrar | encontrados antes de integrar |
| **Defeitos escapados** | encontrados depois | encontrados depois |
| **Retrabalho** | precisou refazer? quanto? | precisou refazer? quanto? |

Depois respondam, por escrito:

- A crew reduziu o **Cycle Time**? Contando o tempo de configurá-la, o saldo ainda é positivo?
- A razão entre defeitos escapados e total **piorou**?
- De que lado do ponto de equilíbrio velocidade × qualidade o grupo ficou?

!!! tip "Resultado negativo também é resultado"
    Se a crew foi mais lenta ou gerou mais defeitos, isso é uma **descoberta válida e defensável** — e provavelmente indica que a tarefa não tinha frentes independentes. Registre e justifique. O que não vale é adotar orquestração sem evidência.

**Entregável:** Tabela comparativa preenchida com as conclusões do grupo.

3. **Um comparativo honesto** preenchendo a tabela:

| Critério | CrewAI | LangChain / LangGraph |
|----------|--------|------------------------|

| Tempo até a primeira execução funcionando | | |
| Onde a configuração vive (YAML, código, grafo) | | |

| Controle sobre o caminho de execução | | |
| Cycle Time medido | | |
| Defeitos escapados | | |

4. **Uma recomendação**, em um parágrafo: qual dos dois o grupo deveria usar **neste produto**, e por quê. Vale recomendar nenhum dos dois.

!!! abstract "Por que este desafio existe"
